# Implementation Plan: Repair of ext4 File Systems After an Unclean Shutdown

**Branch**: `006-ext4-repair` | **Date**: 2026-10-17 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/006-ext4-repair/spec.md`

## Summary

Repair the ext4 root partition of an image after power loss — replay the journal, drop orphan
inodes, and produce correct bitmaps, counts and the clean flag — by reading the source through a
jbd2 **journal overlay** and rebuilding the file system into a new image with the existing shrink
pipeline (feature 002). A same-size rebuild gives a repaired copy; a smaller target gives a repaired
and shrunk image in one operation. Anything beyond power-loss damage is classified from the
existing consistency checker and refused. The Image tab gets a "File system" analysis and a
**Repair the file system** option of **Create image**; the Restore tab's shrink-and-write flow
repairs as part of the shrink.

## Technical Context

**Language/Version**: C# 7.3, .NET Framework 4.8

**Primary Dependencies**: BCL and Windows Forms; own ext4 reader/writer/checker (feature 002); no
new packages, no GPL code

**Storage**: image files; `HddBackup.ini` unchanged

**Testing**: xUnit with ext4 fixtures generated by e2fsprogs in Docker (developer-only), independent
`e2fsck -fn` and tree comparison in the `ext4-check` CI job; manual hardware checklist step

**Target Platform**: Windows 7 SP1 – Windows 11, x86/x64

**Project Type**: desktop app (single WinForms executable; Core compiled in)

**Performance Goals**: repair of a 16 GB image no slower than shrinking it (SC-004); the journal
(typically 32–128 MiB) is read once

**Constraints**: the source image is never written; result kept only after full check and tree
comparison; no device writes

**Scale/Scope**: jbd2 parser + overlay (~500 lines), orphan handling, finding classification,
planner/shrinker flags, Image/Restore tab changes, ~16 strings × 6 languages, 5 new fixtures,
constitution amendment
